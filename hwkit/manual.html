HWKit GUI — Manual & Documentation

HWKit GUI is a graphical tool built on IBM's aihwkit analog-AI simulator. It does three things:

  1. Fit aihwkit device models to measured pulse-response data of a real analog synapse device (LTP/LTD conductance curves).
  2. Simulate neural-network training on crossbar arrays built from that fitted device, including peripheral non-idealities (DAC/ADC resolution and noise, read noise).
  3. Compare synapse architectures ("device modes"): single device, averaged pair, true differential pair, and the Tiki-Taka training algorithms.

Provenance. HWKit GUI builds on aihwkit [1, 2]: the device physics models, the training compounds (vector, one-sided and transfer unit cells, refresh and chopper mechanics), the peripheral I/O model and the analog optimizers are aihwkit implementations. HWKit GUI's own design contributions are the fitting pipeline and its normalization (§3), the GUI and workflow, and the device-mode and parameter wiring documented here. Sections below tag aihwkit-provided behaviour with references [1]–[4].

1. Installation & Setup

Requirements: Python 3.11, aihwkit 1.1.0 (CPU build) [1], PyTorch (installed as an aihwkit dependency), and a conda distribution such as Miniforge. The GUI runs on macOS (tested) and Windows (supported; testing pending).

macOS

./setup.sh            # installs Miniforge (via Homebrew) + conda env "aihwkit"
conda activate aihwkit
python main.py        # launches the GUI

Windows (Miniforge/Anaconda prompt)

conda create -n aihwkit python=3.11
conda activate aihwkit
pip install aihwkit
python main.py

On macOS, aihwkit and PyTorch each bundle their own OpenMP runtime, which crashes on import unless KMP_DUPLICATE_LIB_OK=TRUE is set — main.py sets it automatically (harmless on Windows), and setup.sh also writes it into the conda environment.

The documentation ships with the app as one combined page (docs.html, generated by build_docs.py) with two switchable tabs: this manual and the API reference. Help → Manual and Help → API Reference open it in the browser on the corresponding tab; the manual also exists standalone as manual.html.

2. Workflow overview

measurement (.txt) ─ Fit ─► fitted device (.fit) ──┐
        configure or load   sim config (.sim) ─────┼─► Simulate ─► live plots + results (.csv)
        configure or load   network (.net) ────────┘

The three inputs are independent: the device comes from a fit (or a loaded .fit), while simulation config and network are configured or loaded on their own — only Simulate brings them together.

Everything currently held in memory is shown in the Current Data panel and can be saved/reloaded through the File menu (.fit, .sim, .net, .csv).

3. Device fitting

3.1 Measurement file format

A plain text file with one conductance value per line (whitespace- or comma-separated also works). The file must contain an even number of values 2·n:

  • values 1 … n — LTP sweep: conductance after each of n potentiation pulses, starting from the device minimum,
  • values n+1 … 2n — LTD sweep: conductance after each of n depression pulses, starting from the device maximum.

When fitting, the GUI asks for the unit the file is written in (S, mS, µS, nS, pS); values are converted internally.

The order of the values is a hard requirement: the LTP half must ascend from the device minimum, and the LTD half must start at the device maximum and descend. The tool does not detect a differently ordered export (e.g. an LTD sweep sorted ascending) — it will produce a meaningless fit without any warning. After every fit, check the preview plot: the fitted curves must follow the measured points.

Assumption (important): the fit interprets the curve as the response to identical pulses — the per-pulse conductance change is attributed entirely to the device state. If the measurement used a pulse-amplitude ramp, see the limitation in §8.2.

3.2 Normalization: offset and scale

Measured conductances G are mapped to simulator weights w by

w = (G − offset) / scale        offset = (G_max + G_min) / 2   [µS]
G = w · scale + offset          scale  = (G_max − G_min) / 2   [µS per weight unit]

so every fitted device spans exactly [−1, +1] regardless of the measurement unit. This keeps training behaviour (learning rates, dw_min, ADC bounds) independent of the unit the file happened to be written in. offset and scale are stored in the .fit file and shown in the Current Data panel, so weights can always be mapped back to physical conductance.

3.3 Running a fit

Fit button → choose the .txt file → one Fit Settings window asks for the file's conductance unit and the four variation (noise) parameters together; closing that window cancels the fit:

Dialog field aihwkit parameter Meaning
Cycle to Cycle Step Standard Deviation dw_min_std pulse-to-pulse variation of the update step (relative to dw_min)
Device to Device Step Standard Deviation dw_min_dtod per-device variation of the update step, fixed at construction
Device to Device Minimum Conductance Std w_min_dtod per-device variation of the lower bound
Device to Device Maximum Conductance Std w_max_dtod per-device variation of the upper bound

The tool then fits every supported device model against the data (SoftBounds, SoftBoundsPmax, ExpStep, LinearStep, ConstantStep, PowStep — all aihwkit device models [1], fitted through aihwkit's fit_measurements [1]; the parameter choices, bounds and normalization are HWKit GUI design) and opens a chooser listing the candidates ranked by RMSE (best first). Selecting a row previews its simulated LTP/LTD response against the measured points. Device types that could not be fit are listed below the choices together with the failure reason — a missing candidate is never a silent mystery.

For ExpStepDevice the fit additionally calibrates the nonlinearity parameters (A_up, A_down, gamma_up, gamma_down, a, b) instead of keeping aihwkit's generic defaults.

3.4 The .fit file

Current format — a dict holding the device plus the physical mapping:

{"device": ExpStepDevice(...), "offset": 0.6972, "scale": 0.5388}

Security: .fit files are parsed through a whitelisting AST evaluator, not eval(). Only the supported device constructors, DriftParameter, numeric literals and numpy scalar wrappers are allowed — a manipulated file cannot execute code.

4.2 Network config (.net)

Configure network… is a single window: a type dropdown (MLP / CNN), layer rows with + Add layer / − Remove last buttons, and the activation. The convolutional section (out-channels / kernel size per layer, each conv followed by the activation + 2×2 max-pooling, odd kernels only, max 4 layers) only appears while CNN is selected; the hidden-layer section lists the fully-connected sizes. All weight layers are analog (AnalogLinear / AnalogConv2d); biases are digital (§8.5).

5. Device modes

The Device Mode field selects how one logical weight is realized in hardware. All modes use the same fitted device — what changes is the synapse architecture and the training algorithm around it. The one exception is Ideal (§5.7), the pure-software baseline that uses no device at all.

5.1 None — single device

Implementation: aihwkit SingleRPUConfig [1].

One device per weight: w = G − reference. Simplest and cheapest; fully exposed to the device's asymmetry and noise. Needs the reference subtraction (§8.1).

5.2 AveragedPair — two averaged devices

Implementation: aihwkit VectorUnitCell [1]; the equal-weight averaging setup is HWKit GUI design.

Two identical devices whose average is the weight (gamma_vec = [0.5, 0.5], alternating updates). Each single-device pulse moves the combined weight by half a step — doubling the effective number of states and averaging some noise. This is not a differential pair — both cells contribute with the same sign; the true differential pair is the OneSided mode (§5.3).

5.3 OneSided — true differential pair

Implementation: aihwkit OneSidedUnitCell incl. the refresh mechanism [1].

The weight is a difference of two cells, w = G⁺ − G⁻. Positive updates only ever potentiate G⁺, negative ones only G⁻ — every write uses the device's good direction, which partially sidesteps an asymmetric device response. The reference subtraction cancels in the pair, so this mode needs no reference column (§8.1).

Because both cells can only fill up, the pair needs a periodic refresh: read the difference, reset both cells, rewrite one. Refresh Every sets how many batches pass between refresh sweeps (during a sweep only weights whose fuller cell exceeds 75 % of its range are rewritten):

  • 1 — check after every batch (safest, highest hardware overhead),
  • N — check every N batches (1/N of the overhead, more saturation risk),
  • 0 — never: both cells saturate and the weights freeze; accuracy visibly decays after the first epochs. Only useful to demonstrate the effect.

5.4 TikiTaka — transfer-based training

Implementation: aihwkit TransferCompound [1]; algorithm from Gokmen & Haensch [3].

Two matrices per layer: a fast matrix A absorbs every SGD update, and its content is periodically (partially) transferred to a slow matrix C — the one actually used in the forward/backward pass. Averages out update noise. Works best on devices with a usable symmetry point; on strongly asymmetric devices plain TikiTaka converges poorly (that is the physics, not a bug — use the TTv2 modes there).

  • Fast LR — learning rate of the update onto A (the SGD LR then only scales the transfer). For plain TikiTaka larger values (≈ 1.0) work better.
  • Transfer Every — batches between transfers.

5.5 TikiTakaV2 — buffered transfer

Implementation: aihwkit ChoppedTransferCompound (choppers off) [1]; algorithm from Gokmen [4].

Like TikiTaka, but the read of the fast matrix lands on a digital buffer first; only buffer entries that crossed a threshold write the slow matrix. This filters device read noise and small spurious transfers. Transfer Every counts single mat-vecs (samples) here, matching aihwkit's convention for this compound. For the TTv2 modes a Fast LR of ≈ 0.1 is the recommended starting point (aihwkit's own TTv2 presets use it); 1.0 can become unstable after a few epochs.

5.6 TikiTakaV2Chopped — buffered transfer + chopping

Implementation: aihwkit ChoppedTransferCompound [1]; algorithm from Gokmen [4].

TikiTakaV2 plus choppers: updates onto the fast matrix are written with a randomly flipping sign and the sign is recovered on readout. The gradient signal survives; the device's systematic bias/asymmetry does not follow the sign flips and averages out in the buffer. Chopper Prob is the per-read probability of a sign flip (0.01 ≈ one flip per 100 reads). This is the mode that most directly addresses a strongly asymmetric device response.

5.7 Ideal — software baseline

Implementation: plain PyTorch layers (nn.Linear/nn.Conv2d) — no aihwkit tiles involved.

Pure floating-point software training: the fitted device and every periphery non-ideality are ignored (the DAC/ADC/noise and crossbar fields have no effect), and no device needs to be loaded. Use it to measure the theoretical maximum of the configured network under the identical training regime (same data, batches, epochs) before letting any device loose on it — the gap between an Ideal run and a device run is exactly what the analog hardware costs.

6. Running a simulation

Simulate requires a device, a simulation config and a network (the GUI lists what is missing). While running:

  • the Notes panel shows aihwkit's analog summary of the exact model about to be trained (layers, tile counts),
  • the training plot shows live test/train accuracy and loss per epoch,
  • Cancel stops after the current epoch and keeps everything recorded so far.

Results accumulate as CSV (epoch;test_acc;train_acc;loss) and can be saved via Save results. Every results file starts with a #-prefixed metadata block — timestamp, the exact fitted device, offset/scale, the full simulation config and the network — so a saved .csv is always traceable to the run that produced it (CSV tools skip # lines).

6.1 Batch runs without the GUI

batch_runner.py runs many simulations one after another without opening a window — for seed repetitions, parameter sweeps or anything else where clicking through the GUI would take longer than the runs themselves. It uses the same .fit, .sim and .net files the GUI writes, calls the same SimulationRunner, and produces the same results CSV. Nothing about the simulation itself changes.

The input is a manifest, one row per run:

RunID;fit;sim;net;seed;out
A1;Devices/SVS.fit;Sims/A1.sim;Nets/MLP_100.net;1;Results/A1_s1.csv
A1;Devices/SVS.fit;Sims/A1.sim;Nets/MLP_100.net;2;Results/A1_s2.csv
A1;Devices/SVS.fit;Sims/A1.sim;Nets/MLP_100.net;3;Results/A1_s3.csv
Column Meaning
RunID free label, only used in the console output and the log
fit, sim, net the three input files; relative paths resolve against the manifest
seed overrides the Seed entry of the .sim; leave empty to keep the file's value
out where the results CSV is written

Because seed overrides the file, one .sim per configuration covers all of its repetitions — the three rows above share a single config file.

Seed: 0 means unseeded, not "seed number zero": simulate() does if seed: torch.manual_seed(seed), and 0 is falsy. Use 1, 2, 3 … for repetitions. The runner rejects a manifest that asks for seed 0.

Run it from the HWKit directory with the aihwkit environment, because the training data is read from ./data relative to the working directory:

conda activate aihwkit
cd HWKit
python batch_runner.py manifest.csv --dry-run          # check paths, run nothing
python batch_runner.py manifest.csv --workers 4        # 4 runs at a time
python batch_runner.py manifest.csv --workers 4 --log batch.log

--workers is how many runs happen at once. Four is a reasonable default on a ten-core machine: measured on a TikiTakaV2Chopped config it is about 2.3× faster than running them one by one, while leaving cores and memory free for other work. More workers mainly cost memory — each one holds its own model and dataset.

Alongside every results CSV the runner writes the effective .sim with the seed applied, so any single run can be reloaded into the GUI and repeated from a file.

Failures are reported and logged, and the exit status is non-zero if anything failed. A failure inside a run — missing file, broken config, an error raised by aihwkit — costs only that run; the others continue. If a worker process dies outright instead (killed for memory, segfault in the native backend), Python never sees an exception and the process pool is torn down: the runs still queued at that moment are logged as failed without having been executed. The log lists which ones, so they can be re-run from a shortened manifest.

8. Physical assumptions and limitations

These are deliberate modeling choices. They should be quoted in any thesis or report that uses HWKit GUI results.

8.1 Reference subtraction

A single memristive device has only positive conductance; representing negative weights as w = G − offset requires subtracting a reference. Two hardware options exist: an analog reference column biased at G_offset, or a digital subtraction — the offset contribution to each output is offset · Σx, and Σx is already known in the digital domain, so one multiply-and-subtract per output removes it exactly. The simulation models an exact, noiseless reference, which corresponds to the digital variant (an analog reference column would add its own noise and drift, which are not modeled). The OneSided mode needs neither: there the reference cancels in the pair G⁺ − G⁻.

8.2 Identical-pulse interpretation of ramp measurements

The available measurement was taken with a pulse-amplitude ramp (potentiation −2 → −3.5 V, depression 0 → 4.5 V, different pulse widths). The fit, however, interprets the curve as the response to identical pulses: the per-pulse change is attributed entirely to the device state, while in the measurement it partly came from the growing amplitude. Consequences:

  • the effective number of analog states — the key figure for analog trainability — may be substantially over- or underestimated,
  • part of the fitted up/down asymmetry may be a protocol artifact (different ramps and pulse widths per direction),
  • a per-update amplitude ramp is not implementable in the open-loop parallel pulsed update that aihwkit (and the analog-training concept) assumes.

8.3 Weight scale

Weights are normalized to −1, +1, so results are independent of the measurement unit.

8.4 Peripheral I/O management

aihwkit's defaults are kept [1]: ABS_MAX noise management (each input vector is rescaled to its absolute maximum before the DAC) and ITERATIVE bound management (a matrix-vector product is repeated with halved scaling when the ADC saturates). Both correspond to real but non-trivial peripheral circuitry; they are the common baseline in the aihwkit literature. The transfer read (Tiki-Taka modes) and refresh read (OneSided) run through the same DAC/ADC non-idealities as the normal forward pass, with noise/bound management disabled for the one-hot transfer reads, following aihwkit's own presets.

8.5 Digital biases and gradient clipping

Layer biases are digital (aihwkit default) and unbounded, unlike the hardware-bounded analog weights. They train with a reduced learning rate (BIAS_LR_SCALE = 0.5) and are the only parameters affected by the gradient-norm clipping in the training loop: analog tile updates bypass .grad entirely (aihwkit replays stored activation/error vectors as pulsed rank-1 updates), and a global norm clip across crossbars would require hardware nobody builds. The clip is a safety net for the digital biases only.

8.6 AnalogAdam

Adam keeps two digital state values per weight, which negates the analog efficiency advantage — a real analog accelerator would not implement it.

8.7 Same technology for all cells

Multi-device modes (AveragedPair, OneSided, Tiki-Taka fast & slow matrices) build every cell from the same fitted device — i.e. all crossbars share one technology. Using a different (e.g. capacitor-based) device for the fast Tiki-Taka matrix is a possible future extension.

8.8 Fit freedom of w_max

The fit may move the model's w_max up to 2× away from the measured maximum (soft-bounds devices approach their bound asymptotically, so the model bound can legitimately lie beyond the last measured point). If a fit result reports w_max exactly at that limit (2.0 in normalized units), the bound was binding — inspect the fit quality before using it.

9. Troubleshooting

Symptom Cause / fix
OneSided: accuracy rises, then decays over epochs Refresh Every = 0 — the cells saturate and weights freeze. Set it to ≥ 1.
TikiTaka converges much worse than None Expected on strongly asymmetric devices; use TikiTakaV2(Chopped), or raise Fast LR (≈ 1.0) for plain TikiTaka.
TTv2 modes unstable after a few epochs Lower Fast LR to ≈ 0.1 (aihwkit's own preset value).
Crash on import: OpenMP / libomp error (macOS) main.py sets KMP_DUPLICATE_LIB_OK=TRUE automatically; if it still occurs, set the variable in the environment.
A device type is missing in the fit chooser It could not be fit; the reason is listed below the candidate list.
CIFAR10 accuracy is low Expected: the small MLP/CNN architectures here do not reach modern CIFAR10 accuracy; use it for relative comparisons only.
Loading a .fit fails with "call not allowed" The file contains something other than a saved device — only files written by HWKit GUI (or matching its format) can be loaded.
Device response preview differs every time the same .fit is loaded The device carries device-to-device variation (dw_min_dtod, w_min_dtod, w_max_dtod > 0); the preview simulates one randomly drawn device instance per load. Expected behaviour, not data corruption.

10. Glossary

Term Meaning
LTP / LTD long-term potentiation / depression — conductance increase / decrease under pulses
Crossbar / tile analog matrix of devices computing a matrix-vector product; large layers are split into tiles
MVM matrix-vector multiplication (one analog forward read)
dw_min smallest conductance step of a device — sets the number of analog states
up_down asymmetry of the up vs. down step size
DAC / ADC digital-analog / analog-digital converters at the crossbar inputs/outputs
Transfer Tiki-Taka: moving accumulated updates from the fast to the slow matrix
Chopper random sign flip applied to updates, removing systematic device bias
Refresh OneSided: reading the pair difference, resetting both cells, rewriting one
